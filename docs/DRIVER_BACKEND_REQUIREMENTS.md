## 1. Purpose

This document outlines the exact backend integration requirements for the **RR Driver Mobile Application** (React Native / Expo / TypeScript) within the unified RapidRescue emergency response platform.

It is designed to give **Ravin** (FastAPI Backend Lead) an unambiguous, implementation-grounded specification of:
1. Every data entity, type, and field currently consumed or generated by the Driver App.
2. The operational state machines (Verification, Duty Status, Availability, Emergency Lifecycle).
3. The HTTP API client, authentication token, and real-time streaming expectations.
4. The strict architectural boundary separating the mobile client from the dispatch engine.

> **CRITICAL ARCHITECTURAL PRINCIPLE**:  
> The RR Driver application **NEVER** decides ambulance allocation, candidate ranking, or cascading fallback. The mobile app strictly acts as an operational edge terminal: reporting telemetry, displaying assigned alerts, and transmitting driver responses (`ACCEPT`, `REJECT`, `TIMEOUT`, `COMPLETE`). All allocation intelligence, race-condition resolution, and state persistence belong to the backend.

## 2. System Architecture

RapidRescue utilizes a **single, unified FastAPI backend** backed by PostgreSQL. The RR Driver mobile application is one of three primary clients interacting with this single backend:

```
                    +------------------------------------+
                    |       RapidRescue Backend          |
                    |         (FastAPI Core)             |
                    +-----------------+------------------+
                                      |
         +----------------------------+----------------------------+
         |                            |                            |
+--------v---------+        +---------v--------+        +----------v---------+
|   Patient App    |        |     RR Driver    |        |    Admin Portal    |
| (Emergency Req)  |        | (Telemetry & Ops)|        | (Verification Rev) |
+--------+---------+        +---------+--------+        +----------+---------+
         |                            |                            |
         +----------------------------+----------------------------+
                                      |
                            +---------v----------+
                            |     PostgreSQL     |
                            |  (Source of Truth) |
                            +--------------------+
```

The backend is the authoritative source of truth for:
- User credentials and role-based access authorization.
- Driver onboarding and 6-document compliance verification status.
- Driver shift duty state (`ONLINE` / `OFFLINE`) and dispatch availability (`AVAILABLE` / `BUSY` / `UNAVAILABLE`).
- Live driver GPS coordinates and breadcrumbs.
- Emergency dispatch lifecycle, timeouts, and atomic driver assignment.

## 3. Driver App Responsibilities

The RR Driver app is responsible for:
1. **User Authentication**: Providing a clean, single common login screen for mobile/password credentials, routing users based on the returned role (`DRIVER` vs `ADMIN`).
2. **Onboarding & Document Capture**: Collecting registration details and uploading 6 distinct compliance documents (images/PDFs) with client-side mime and size validation (≤ 10 MB).
3. **Operational Gating**: Programmatically preventing unverified drivers from toggling duty, starting GPS tracking, or receiving dispatches.
4. **Foreground Telemetry**: Capturing high-accuracy device GPS fixes while on active duty and formatting telemetry payloads (`latitude`, `longitude`, `accuracy`, `altitude`, `heading`, `speed`, `timestamp`).
5. **Driver State Reporting**: Transmitting driver shift intent (`GO ONLINE`, `GO OFFLINE`) and availability changes.
6. **Emergency Alert Presentation**: Displaying incoming emergency alerts with a priority-calibrated response countdown timer (20s / 40s / 60s).
7. **Driver Action Reporting**: Emitting user responses (`ACCEPT`, `REJECT`, `TIMEOUT`) and final incident resolution (`COMPLETE`).

---

## 4. Backend Responsibilities

The FastAPI backend must handle:
1. **Unified Authentication & RBAC**: Evaluating credentials from a single login endpoint and returning the role (`DRIVER` or `ADMIN`), user identifiers, and JWT bearer token.
2. **Driver Account Persistence**: Storing personal records, experience, and initial compliance states.
3. **Document Ingestion & Storage**: Receiving multipart document uploads, generating secure URLs, and storing document review states.
4. **Verification Authority**: Providing administrative endpoints for document approval/rejection and serving as the absolute source of truth for verification status.
5. **Live Telemetry Ingestion**: Ingesting high-frequency driver coordinates without blocking dispatch pipelines.
6. **Dispatch Engine & Spatial Matching**: Selecting suitable ambulances based on proximity, hospital capabilities, driver verification, and availability.
7. **Atomic Allocation & Race Resolution**: Ensuring an emergency is assigned to exactly one driver, preventing double booking, and handling simultaneous driver accepts.
8. **Cascading Dispatch Fallback**: Re-routing requests to candidate #2 if candidate #1 rejects or times out.
9. **Real-Time Dispatch Broadcasting**: Pushing emergency alerts to the target driver app via WebSocket or SSE.

## 5. Authentication

### Current Mobile Implementation
- The app uses a **single common login interface** (`app/(auth)/login.tsx`).
- There are no visible admin login buttons, separate URLs, or role selection dropdowns.
- The user enters `mobileNumber` and `password`.
- On successful login, the returned `role` controls navigation:
  - `role === 'DRIVER'` $\rightarrow$ `app/(driver)/dashboard.tsx`
  - `role === 'ADMIN'` $\rightarrow$ `app/(admin)/dashboard.tsx`

### Backend Expectations
1. **Endpoint Capability**: Authenticate credentials and return user role.
2. **Payload Received from App**:
   ```json
   {
     "mobileNumber": "9876543210",
     "password": "Password@123"
   }
   ```
3. **Payload Returned to App**:
   ```json
   {
     "success": true,
     "session": {
       "userId": "RR-DRV-1001",
       "role": "DRIVER",
       "driverId": "RR-DRV-1001",
       "name": "Gokul",
       "displayName": "Gokul",
       "mobileNumber": "9876543210",
       "email": "gokul.driver@rapidrescue.org",
       "yearsOfExperience": 5,
       "token": "jwt_bearer_token_string",
       "createdAt": "2026-09-26T12:00:00.000Z",
       "isMockSession": false
     },
     "message": "Login successful"
   }
   ```
4. **Security Rules**:
   - Passwords must **never** be returned in session payloads.
   - Tokens must be standard JWT bearer tokens compatible with `Authorization: Bearer <token>`.
   - Exact token claim structure is **NOT FINALIZED** by the client; the backend may structure claims as needed (e.g. `sub`, `role`, `exp`).

## 8. Driver Verification

The verification workflow is administrative and legal gatekeeping before a driver can be dispatched.

### Verification Status Lifecycle (`VerificationStatus` in `src/types/verification.ts`)
```
[NOT_SUBMITTED]
       │
       ▼ (Driver uploads all 6 documents & submits)
   [PENDING]
       │
       ▼ (Admin opens driver review queue)
 [UNDER_REVIEW]
       │
       ├────────────────────────────────────────┐
       ▼ (Admin Approves all documents)         ▼ (Admin Rejects ≥ 1 document)
  [VERIFIED]                                [REJECTED]
       │                                        │
(Operational Access Unlocked)           (Driver corrects rejected document)
                                                │
                                                ▼
                                            [PENDING]
```

### Required Documents Matrix (`REQUIRED_DOCUMENT_DEFINITIONS` in `src/constants/verification.ts`)
The client enforces exactly **6 required compliance documents**:

| Document Type (`VerificationDocumentType`) | Category | Description | Allowed Mime Types | Max Size |
|:---|:---|:---|:---|:---|
| `DRIVING_LICENSE` | `DRIVER` | Commercial / Heavy Motor Vehicle (HMV) licence with badge | `image/jpeg`, `image/png`, `image/webp`, `application/pdf` | 10 MB |
| `GOVERNMENT_ID` | `DRIVER` | Government photo ID (Aadhaar / Voter ID / Passport) | `image/jpeg`, `image/png`, `image/webp`, `application/pdf` | 10 MB |
| `DRIVER_SELFIE` | `DRIVER` | Front-facing photograph in official uniform | `image/jpeg`, `image/png`, `image/webp` (No PDF) | 10 MB |
| `AMBULANCE_REGISTRATION` | `AMBULANCE`| Vehicle Registration Certificate (RC) showing ambulance class | `image/jpeg`, `image/png`, `image/webp`, `application/pdf` | 10 MB |
| `AMBULANCE_PERMIT` | `AMBULANCE`| Regional transport commercial permit and fitness certificate | `image/jpeg`, `image/png`, `image/webp`, `application/pdf` | 10 MB |
| `VEHICLE_INSURANCE` | `AMBULANCE`| Commercial insurance covering passenger and 3rd party liabilities | `image/jpeg`, `image/png`, `image/webp`, `application/pdf` | 10 MB |

### Document State Model (`VerificationDocument`)
Each document in `documents[type]` contains:
- `id`: Unique document ID.
- `type`: One of the 6 enum keys above.
- `name`: Display name.
- `category`: `'DRIVER'` or `'AMBULANCE'`.
- `status`: `'NOT_UPLOADED'` \| `'UPLOADING'` \| `'UPLOADED'` \| `'REJECTED'`.
- `uri`: File location / CDN URL.
- `fileName`: Original file name.
- `mimeType`: Detected MIME type.
- `size`: Size in bytes.
- `uploadedAt`: ISO timestamp string.
- `rejectionReason`: Optional string provided by admin if rejected.

### Backend Requirements for Verification
1. **Multipart Upload Endpoint**: Accept document files, persist them, and return `VerificationDocument` metadata.
2. **Review Submission Endpoint**: Mark driver profile as `PENDING`.
3. **Admin Actions**: Support `startReview` (`UNDER_REVIEW`), `approveDriver` (`VERIFIED`), and `rejectDriver` (`REJECTED` with `rejectionReason` and `rejectedDocumentType`).
4. **Resubmission**: When a driver re-uploads a rejected document and resubmits, reset status to `PENDING` and clear `rejectionReason`.

## 10. Duty Status

### Current Data Model (`DriverDutyStatus` in `src/types/location.ts`)
```typescript
type DriverDutyStatus = 'OFFLINE' | 'ONLINE';
```

### Business Rules & Transition Matrix
1. **Verification Gate**:
   - A driver whose `verificationStatus !== 'VERIFIED'` is **STRICTLY PROHIBITED** from transitioning to `ONLINE`.
   - The backend must reject any status update to `ONLINE` if the driver is `PENDING`, `UNDER_REVIEW`, `REJECTED`, or `NOT_SUBMITTED` (HTTP 403 Forbidden).
2. **Going ONLINE Sequence**:
   - Driver requests `ONLINE`.
   - Client verifies foreground location permissions and hardware GPS readiness.
   - Client obtains initial GPS fix.
   - Backend receives `ONLINE` update alongside initial GPS coordinate fix.
   - Result: `dutyStatus = 'ONLINE'`, `availability = 'AVAILABLE'`.
3. **Going OFFLINE Sequence**:
   - Driver taps `GO OFFLINE`.
   - Client stops location tracking watcher.
   - Backend updates state: `dutyStatus = 'OFFLINE'`, `availability = 'UNAVAILABLE'`.
   - Any unassigned incoming alerts must be revoked immediately by backend.

## 11. Availability

### Current Data Model (`DriverAvailability` in `src/types/location.ts`)
```typescript
type DriverAvailability = 'UNAVAILABLE' | 'AVAILABLE' | 'BUSY';
```

### State Relationship Matrix

| Verification Status | Duty Status | Availability | Dispatch Eligible? | Notes |
|:---|:---|:---|:---:|:---|
| `NOT_SUBMITTED` / `PENDING` / `REJECTED` | `OFFLINE` | `UNAVAILABLE` | **NO** | Operational controls locked in mobile UI. |
| `VERIFIED` | `OFFLINE` | `UNAVAILABLE` | **NO** | Off duty. Battery/privacy protected. No alerts sent. |
| `VERIFIED` | `ONLINE` | `AVAILABLE` | **YES** | Idle, GPS active, prioritized for emergency calls. |
| `VERIFIED` | `ONLINE` | `BUSY` | **NO** | Committed to an active emergency (`ACCEPTED`). Must NOT receive another dispatch. |

### Availability State Transitions
- `OFFLINE` $\rightarrow$ `ONLINE`: Becomes `AVAILABLE`.
- `AVAILABLE` + Incoming alert: Remains `AVAILABLE` until `ACCEPT`.
- Driver taps `ACCEPT`: Becomes `BUSY`.
- Driver completes incident (`COMPLETE`): Transitions from `BUSY` $\rightarrow$ `AVAILABLE`.
- Driver taps `GO OFFLINE`: Forces availability to `UNAVAILABLE`.

## 14. Emergency Response

### Response Payload (`EmergencyResponsePayload` in `src/types/emergency.ts`)
When an alert is active, the driver app emits one of three actions:

```typescript
export interface EmergencyResponsePayload {
  requestId: string;     // e.g. "EMG-4821"
  driverId: string;      // e.g. "RR-DRV-1001"
  action: EmergencyAction; // "ACCEPT" | "REJECT" | "TIMEOUT"
  timestamp: number;     // Date.now()
}
```

### Action Handling Specifications

#### 1. ACCEPT
- **Client Action**: Driver taps `ACCEPT EMERGENCY`. Alert modal dismisses.
- **Client State**: Local state becomes `ACCEPTED`. Driver availability transitions to `BUSY`.
- **Backend Requirement**:
  - Atomically lock the emergency assignment to this driver.
  - Notify the Patient App that ambulance is dispatched.
  - Return confirmation `{ success: true, requestId, action: 'ACCEPT' }`.

#### 2. REJECT
- **Client Action**: Driver taps `REJECT`. Alert modal dismisses.
- **Client State**: Local state becomes `REJECTED`. Driver availability remains `AVAILABLE`.
- **Backend Requirement**:
  - Log driver rejection.
  - Trigger cascading dispatch engine to allocate candidate #2.
  - Do NOT penalize the driver or mark them offline.

#### 3. TIMEOUT
- **Client Action**: Countdown timer reaches `0s`. Alert dismisses automatically.
- **Client State**: Local state becomes `EXPIRED`. Driver availability remains `AVAILABLE`.
- **Backend Requirement**:
  - Treat as no-response timeout.
  - Trigger cascading dispatch engine to allocate candidate #2.

## 16. Real-Time Communication

### Architectural Layer (`src/services/realtime/realtimeService.ts`)

### Expected Event Contracts for Backend

#### 1. Incoming Emergency Event (`onEmergencyRequest`)

- **Client emits**: `{ requestId: string, driverId: string, action: 'ACCEPT' | 'REJECT' | 'TIMEOUT' }`.

## 17. API Client Expectations

The Driver API client (`src/services/api/apiClient.ts` & `src/services/api/apiError.ts`) enforces the following standards:

     `Authorization: Bearer <token>`

3. **Standard JSON Content Types**:
   - Requests provide `Content-Type: application/json` and `Accept: application/json`.
4. **Standard Error Payloads**:
   - FastAPI errors structured as:
     ```json
     {
       "detail": "Error explanation message"
     }
     ```
     are automatically parsed into `ApiError.message` and displayed to the user cleanly without raw tracebacks.
5. **Timeout Budget**: Default client timeout is **15,000ms** via native `AbortController`.

## 19. Concurrency & Dispatch Requirements

Because RapidRescue operates in high-stress, multi-patient, multi-driver environments, the following edge cases **MUST be handled by the backend**:

1. **Atomic Assignment & Race Conditions**:
   - If two drivers tap `ACCEPT` nearly simultaneously for the same incident, the backend must use database transactions / row locks (`SELECT ... FOR UPDATE`).
   - The first driver wins (`200 OK`). The second driver receives `409 Conflict` (`"Incident already assigned to another responder"`).
2. **Stale Location Handling**:
   - If a driver's GPS timestamp is older than a configurable threshold (e.g., > 60 seconds), the dispatch engine must flag the driver as stale and avoid allocating them to critical emergencies.
3. **Offline while Alert Active**:
   - If a driver loses connectivity or closes the app during an incoming 20-second countdown, the backend timer must expire and automatically re-allocate to candidate #2.
4. **Duplicate Allocation Prevention**:
   - When an ambulance is marked `BUSY`, its record must be excluded from all candidate selection queries until a `COMPLETE` event is acknowledged.

## 24. Not Yet Defined / Requires Backend Decision

The following technical contracts are **intentionally not defined by the Driver App** and must be finalized by Ravin:

1. **Exact Endpoint URLs**:
   - The Driver App has abstracted all API calls into services without hardcoding URL paths (e.g. whether endpoints follow `/api/v1/drivers/...` or `/api/v1/dispatch/...` is up to backend design).
2. **WebSocket URL & Handshake Protocol**:
   - The WebSocket authentication mechanism (query param token `?token=...` vs subprotocol vs connection init frame) must be specified by the backend.
3. **Telemetry Push Frequency**:
   - The optimal frequency for mobile location uploads while on duty (e.g. every 5 seconds vs distance-based delta movement) needs backend capacity agreement.
4. **JWT Expiration & Refresh Flow**:
   - Token TTL and whether refresh tokens (`/auth/refresh`) are implemented.
5. **Hospital & Bed Allocation API**:
   - How destination hospital information and triage handoff will be attached to an accepted emergency.
